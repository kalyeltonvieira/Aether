# Contrato de desenvolvimento Studio v1

Base HTTP `/api/v1`, WebSocket `/ws`. JSON sem envelope geral; páginas usam `{items:[], total:int, offset:int, limit:int, next_offset:int|null}`. Scalar raw JSON preserva bool/int/float/str/null; fatos incluem `object_type` e POST/PATCH aceita `object_type` opcional para o browser não perder identidade int/float. Todas as mutações protegidas por sessão operador, CSRF header `X-CSRF-Token` e validação.

## Autenticação

`POST /api/v1/auth/login` `{token:string}` troca token local definido no ambiente/arquivo privado por cookie HttpOnly de sessão; retorna `{authenticated:true, role:'operator', csrf_token:string}`. Cookie local HTTP SameSite strict, mas ambiente HTTPS Preview explicitamente configurado usa Secure/SameSite=None. `GET /api/v1/auth/session` devolve `{authenticated:true, role, csrf_token}` ou 401. `POST /api/v1/auth/logout` exige CSRF e encerra. O cliente mantém o token somente no campo de login e limpa após troca; não guarda token/segredos em local/sessionStorage. WebSocket autentica cookie de sessão e valida Origin; conexões só de origem permitida. CORS lista finita, nunca `*`. O servidor não aceita execução de código nem caminhos arbitrários. `/health` é público e minimalista.

## Endpoints

- `GET /status` → `{core:{status,version,entities,facts,conclusions}, api:{status,version,uptime_seconds}, rust:{status,available,operations,last_error}, queries_executed, events_processed, last_query_latency_ms:number|null, memory:MemoryStats, cpu_percent:number|null, activity:[], alerts:[]}`. Rust status é disponibilidade/compilação realmente verificada, não presumida.
- `GET /entities?search=&offset=0&limit=100` página de `{entity_id,properties:object}`. `POST /entities` `{entity_id,properties:{}}`; `PATCH /entities/{id}` `{properties:{}}`; `GET /entities/{id}`.
- `GET /facts?subject=&predicate=&offset=0&limit=100` página de `{fact_id,subject,predicate,object,object_type,properties:object,confidence,provenances:[],evidence_records:[{evidence_id,provenance,confidence,context}]}`. `POST /facts` `{subject,predicate,object,object_type?,properties?,confidence?,provenance?:{source,evidence_type?,timestamp_ns?,detail?}}`; `PATCH /facts/{id}` substitui de maneira validada sem perder evidência inadvertidamente e informa novo ID quando chave muda; `DELETE /facts/{id}` remove o fato; `DELETE /facts/{id}/evidence/{evidence_id}` retira um registro, mantendo o fato enquanto houver suporte restante. IDs inválidos retornam 422, registros ausentes 404.
- `POST /consistency/assessments` avalia uma claim concreta e regras `incompatibilities:[{predicate_a,predicate_b,object_pairs?}]`; retorna status `explicit|derived|unknown|contradicted|insufficient_evidence`, completude, suficiência de evidência, IDs de fatos conflitantes, provas e revisão vigente. Regras de incompatibilidade precisam ser declaradas; a rota não escolhe fontes automaticamente.
- `POST /consistency/resolutions` aceita o mesmo payload da avaliação, mais `selected_fact_ids` e `reason`; operador + CSRF. Reavalia o conflito sob lock, exige evidência/proveniência suficiente, obtém o ator da sessão e persiste a revisão sem apagar conflito/fatos. A resposta permanece `contradicted` e inclui a decisão auditada. `GET /consistency/resolutions` lê o ledger inteiro, inclusive itens invalidados por mudança de evidência.
- `GET /history?offset=0&limit=100` página de registros reais `{sequence,timestamp_ns,operation,...}` do store.
- `GET /graph?predicate=&center=&limit=250` → `{nodes:[{id,label,properties}], edges:[{id,source,target,predicate,fact_id}], truncated:boolean}`. Só objetos string que são entidade viram nós. Filtro center retorna vizinhança para expansão sem inventar grafo.
- `GET /rules` → `{items:[{rule_id,revision,enabled,antecedents:[{subject,predicate,object}],consequent:{...}}]}`. `POST /rules` com formato acima (revision opcional); `DELETE /rules/{id}`.
- `POST /queries` `{subject,predicate,object,object_type?,strategy:'forward'|'backward'|'hybrid'|'adaptive',offset:0,limit:100}` → `{solutions:[{key:[s,p,o],bindings:object,explicit:boolean,fact_id:int|null,proofs:[],explanation:[]}], proven:boolean,complete:boolean,stop_reason:string|null,next_offset:int|null,operations:int,facts_examined:int|null,conclusions_produced:int|null,strategy:string,decision_ns:int,execution_ns:int,rationale:string|null}`. Metas abertas backward/hybrid rejeitadas com erro útil; sem resultados simulados. Query invoca engine/controller real; regras podem ser criadas pela UI.
- `POST /inference` → `{complete,stop_reason,conclusions:[],operations,...}` recomputação real. `POST /explanations` `{subject,predicate,object,object_type?}` → `{key,proofs:[],explanation:[],complete,stop_reason}`. Nós explicativos realistas mantêm fato, regra/revisão, suporta IDs/chaves, depth, provenance/provenances e alternativas.
- `GET /memory` → estatísticas reais AdaptiveMemory mais `{patterns:object, persistent:boolean}`. `PUT /memory/budget` `{max_bytes:int}` reconfigura o orçamento residente (sem apagar cold store). Leitura de cache/payloads não é exposta sem necessidade.
- `GET /events?event_type=&status=&after=0&limit=100` → `{items:[EventRecord],next_after:int|null,complete:boolean,queue:object}`. EventRecord usa campos nativos sequence/event_id/event_type/timestamp_ns/source/payload/provenance/status/attempts/created_ns/processed_ns/last_error. `POST /events` `{event_type:'entity.add'|'fact.add'|'fact.remove',source:'studio',payload:object,event_id?:string}` enfileira. `POST /events/process` `{limit:100}` processa handler KnowledgeEventProcessor e retorna EventBatchResult. `POST /events/{id}/retry` requeue de falha.
- `GET /metrics?period=60` → `{samples:[{timestamp_ns,cpu_percent:number|null,rss_bytes:number|null,queries:int,events:int,last_query_latency_ms:number|null,throughput_queries_per_second:number|null,rust_operations:int}], strategies:[{strategy,queries,p50_ms,p95_ms,decision_ns,maintenance_ns}], retention_limit:int}`. Dados são observados em ring buffer; vazio é vazio. Period segundos aceito nos limites.
- `GET /config` → `{memory_max_bytes,max_depth,max_operations,max_conclusions,default_strategy,join_planner,persistence_enabled,rust_enabled,event_batch_size}`. `PUT /config` aceita os campos acima, validando ranges. `persistence_enabled` é startup-only: toggles via API retornam 422; para mudar o modo, ajuste `config.json` no diretório de dados com o Studio parado (por padrão `.aether-data/config.json`) e reinicie. Falso usa store de conhecimento/regras vazio sem snapshots, fila SQLite `:memory:` e memória sem cold store em disco; `config.json` preserva a opção e arquivos de dados antigos não são apagados. Paths e segredos não são configuráveis via API.

WebSocket publica `{type:'snapshot'|'knowledge.changed'|'consistency.changed'|'events.changed'|'metrics', timestamp_ns, data:object}` derivado de estado real. Cliente refaz consultas relevantes em notificação e indica online/offline com reconexão e cleanup; não usa WebSocket como execução arbitrária.

Erros HTTP `{detail:string|object}` com 400/401/403/404/409/422/429 úteis. Formulários, loading, vazio e erros devem ficar explícitos. UI pt-BR com termos técnicos do usuário (Knowledge Explorer etc.). Rotas `/`, `/knowledge`, `/graph`, `/reasoning`, `/proofs`, `/memory`, `/events`, `/performance`, `/settings`; login aparece como gate antes das rotas. Browser usa URLs relativas e credentials include. Sem imagens decorativas, dados/atividade reais; fixtures só com opção CLI/documentação claramente como dados de teste.

## Ajuste de autenticação gerenciada

No ambiente Manus gerenciado o login padrão é **Manus OAuth**, não um sistema novo de email/senha: `GET /api/v1/auth/login-url` retorna `{url}` com state/nonce ligado ao browser e callback fixo; callback `/api/v1/auth/callback` valida e reserva o state antes de I/O externo, impedindo segunda troca concorrente no mesmo processo, resolve identidade e cria sessão. Em falha do provedor, o state permanece consumido e um novo fluxo de login é necessário. Auto-login de Preview aceita somente JWT HS256 verificado por `MANUS_JWT_SECRET`, com expiry e `appId` correspondente; a sessão opaca resultante expira no máximo no `exp` validado ou no TTL máximo local. Não há introspecção do JWT depois da troca do cookie, portanto revogação antecipada pelo provedor não é detectada. Autorização usa allowlist/owner configurado no servidor, nunca concede operador só pelo cookie. `GET /auth/session` retorna `{authenticated,role,csrf_token,auth_mode}`; `GET /auth/info` é público e devolve somente `{mode:'manus'|'token',login_available:boolean}`. Login com token é reservado à instalação independente/administrador por configuração explícita, não substitui OAuth no Preview. Browser deve abrir login OAuth quando mode manus. Mutação exige CSRF em ambos os modos. JWT cookie é HttpOnly e, no Preview HTTPS explicitamente configurado, Secure/SameSite=None. WebSocket aceita a mesma sessão autorizada, com verificação estrita de Origin.
